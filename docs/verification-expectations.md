# Verification Expectations

_Generated by automated analysis on 2026-09-15. Confidence levels: Enforced / Implied / Documented-only._

## Summary

The repository has exactly one CI pipeline: a single GitHub Actions job, `fixture-verification`
(`.github/workflows/ci.yml`), that installs the locked `uv` environment, runs a targeted
storage-migration test, runs the full `pytest` suite (255+ test functions across 13 files),
byte-compiles the source tree, and checks for whitespace/conflict-marker errors with
`git diff --check`. There is no linter, type checker, formatter check, SAST/dependency scanner,
license scanner, coverage threshold, pre-commit/pre-push hook, CODEOWNERS file, or
release/deploy pipeline anywhere in the repository — despite `.gitignore` carrying
`.mypy_cache/`/`.ruff_cache/` entries that imply such tools are used ad hoc by some
contributors without any checked-in configuration or CI step. No branch-protection-as-code
(`.github/settings.yml`, ruleset export, etc.) exists in the repo, and no GitHub API tooling in
this session can confirm whether `fixture-verification` is actually a *required* status check;
the repository has exactly one collaborator (the owner, with `admin` role), who both opens and
merges every pull request, so even a required check could be bypassed by an administrator. The
biggest gap is between the extensive, highly specific verification language in `AGENTS.md`,
`CONTRIBUTING.md`, and `SECURITY.md` (leakage gates, accessibility checks, secret scanning,
"MUST" test requirements, mandatory human review before publication) and what is actually
wired into CI: nearly everything described in those documents is implemented as ordinary
`pytest` test functions that live inside the one full-suite run, with no independent gate, and
several of the most safety-critical claims (mandatory human review, mutation-testing campaigns,
live-provider smoke checks) have no automated enforcement at all.
