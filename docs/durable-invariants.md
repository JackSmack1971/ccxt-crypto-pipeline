# Durable Repository Invariants

_Generated by automated analysis on 2026-09-15. Confidence levels: Confirmed / Implied / Documented-only._

## Summary

This repository is a local-first crypto data-ingestion and research pipeline: a Phase 1 ingestion layer (CEX via `ccxt`, EVM via raw JSON-RPC + explorer adapters, Solana via Helius, and a "Tier 0" DEX poller) writes to a single canonical DuckDB database (`storage/schema.py`/`storage/db.py`, versioned schema currently at `SCHEMA_VERSION = 13`), with OHLCV additionally published to a derived Parquet cache. Phases 2–4 (`analysis/`, `reporting/`) are strictly read-only, offline consumers of that store that build immutable, content-hashed research and report artifacts. The system leans heavily on content-addressed, fail-closed contracts instead of runtime type checking: point-in-time correctness (no look-ahead), monotonic ingestion cursors, canonical-vs-orphaned EVM block bookkeeping, immutable/hash-verified run artifacts, and a claim-ledger that only allows numeric prose whose value is provably derivable from staged evidence. The highest-risk invariants are: (1) DuckDB-is-authoritative/Parquet-is-derived, whose violation would silently desynchronize the two stores; (2) the one-way Phase 1 → Phase 2–4 data boundary (no live-provider calls from analysis/reporting), which is architecturally enforced only by the absence of imports, not a runtime guard; (3) monotonic ingestion cursor/continuation and EVM canonical-block bookkeeping, whose violation would silently duplicate or drop on-chain data; (4) the DatasetSnapshot point-in-time gates that prevent look-ahead into backtests/research; and (5) the CI-enforced storage-migration guard, which is the only mechanism ensuring in-place schema upgrades never silently drop rows.

## Documented-only Risks

- **`AGENTS.md`'s phase-sequencing rule** ("Phases 2, 3, and 4 MUST be implemented in order," §"Sequential phase execution") is a process convention for how contributors/agents should work, not something enforced by code or tests. Nothing prevents a contributor from adding Phase 4 code (`reporting/`) without any Phase 3 code existing; the only real coupling is that `reporting/package/handoff.py` requires a Phase 3-shaped `manifest.json` with `manifest_version == "phase3-v1"` at *runtime*, which is a data-shape check, not a repository-structure guarantee.
- **`FeatureDefinition.compute` version-discipline** (see API/Contract table above): the claim that "a version bump is required whenever a catalog entry's compute behavior changes" (`analysis/alpha/features.py:33-39`, `analysis/alpha/registry.py:23-26`) is asserted only in comments/docstrings. No test or runtime check detects a change to a lambda body in `_FEATURE_CATALOG` without an accompanying version bump; this is a pure code-review discipline invariant.
