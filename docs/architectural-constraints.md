# Architectural Constraints

_Generated by automated analysis on 2026-09-15. Confidence levels: Enforced / Implied / Documented-only._

## Summary

`ccxt-crypto-pipeline` is a single-process, local-first Python monolith with a layered pipeline shape rather than a distributed service architecture: `ingestion/*` (CEX, EVM, Solana, Tier‑0 DEX aggregators) is the only layer that performs external I/O, all of it converges on a single DuckDB+Parquet persistence boundary owned by `storage/db.py`/`storage/schema.py`, and `normalization`, `analysis`, and `reporting` sit downstream and read that store (directly, read‑only, or via approved file artifacts) without ever calling a provider. There is no lint/import-boundary tool (no ESLint/import-linter/dependency-cruiser equivalent), no containerization or IaC, and CI (`.github/workflows/ci.yml`) only runs `pytest`, `compileall`, and a whitespace check — so most boundary rules are **Implied** (consistently followed in code, nothing would flag a violation) rather than mechanically **Enforced**. The highest-impact exceptions that genuinely are enforced: a versioned, monotonically-gated DuckDB schema-migration ladder that refuses to open a database from a newer schema version (`storage/schema.py`); pytest-level network-sabotage tests that fail the build if Phase 2–4 code touches a socket; a DuckDB `read_only=True` connection that would raise if `analysis/datasets/snapshot.py` ever tried to write; and a Phase 4 package generator that raises `ValueError` unless its input manifest is immutable, approved, and reviewer-attested. The biggest risk area is that the repository's own `AGENTS.md`/`CONTRIBUTING.md`/`SECURITY.md` describe several boundaries (no-ingestion-imports-in-analysis, provider-adapter isolation, storage-single-writer discipline) as hard rules, but nothing in tooling would catch a future PR that quietly violates them — see Documented-only Risks.

## Documented-only Risks

These are stated as firm rules in `AGENTS.md`, `CONTRIBUTING.md`, or `SECURITY.md` but have **no** corresponding lint rule, type check, CI gate, or test that would fail if violated. They are the highest-priority gaps for future hardening:

- **"Phase 1 ingestion remains the only layer allowed to call market, provider, explorer, RPC, or on-chain APIs"** (`AGENTS.md:13`, `CONTRIBUTING.md:27-28`, `SECURITY.md:78-80`). Verified true today by import-graph inspection (see Module & Dependency Boundaries / Communication Topology), but nothing besides the unwired `reporting_guard.py` AST check would catch a future `import requests` inside `analysis/` or `reporting/`. The socket-sabotage tests (`tests/test_phase2.py` etc.) only catch *actual* socket use exercised by the specific fixtures those tests run, not a static import.
- **"Analysis strategies MUST NOT import or call ingestion/provider adapters"** and **"Phase 4 MUST NOT import or call ingestion/provider adapters"** (`AGENTS.md:182,308`). Same gap as above — true by inspection, not mechanically enforced.
- **"Do not create a separate database to bypass storage review"** (`AGENTS.md:156`, `CONTRIBUTING.md:224-225`). No test scans for a second `duckdb.connect(...)` call site or a second schema-defining module; `storage_migration_guard.py` could detect this (it checks `SCHEMA_VERSION` movement and storage/test surface changes) but is not invoked by CI, a pre-commit hook, or any test.
- **"New persistent tables or fields require the repository storage migration procedure and a schema-version bump"** (`AGENTS.md:154`). The migration ladder itself is enforced (schema-version gate raises on downgrade), but nothing prevents a developer from adding a column via a stray `ALTER TABLE` outside `storage/schema.py` without bumping `SCHEMA_VERSION` — this would only surface later as an inconsistent-schema bug, not a build failure.
- **Provider-adapter isolation** ("Provider work must remain behind the existing normalized interfaces and routing contracts," `CONTRIBUTING.md:230-231`) for the Tier‑0 DEX clients specifically has no shared `Protocol`/ABC (see Extensibility table) — the EVM adapters do have one (`EVMEnrichmentProvider`), but even that is unchecked because no static type-checker (`mypy`, `pyright`) runs in CI.
- **Historical finding — resolved in the current public surface:** an earlier version of `docs/ARCHITECTURE.md` stated `SCHEMA_VERSION = 6` while the actual code and tests defined 13. The architecture document now records the authoritative version 13; this report remains evidence that documentation must be reconciled against code rather than treated as ground truth by default.

## Open Questions

- Should the AST-based boundary guards (`reporting_guard.py`'s `FORBIDDEN_IMPORT_ROOTS`, `storage_migration_guard.py`'s `SCHEMA_VERSION`/network checks) be wired into CI or a pre-commit hook? As written they are agent-facing skill scripts under `.agents/skills/`, invoked manually/by an AI coding agent, not by the repository's actual CI pipeline (`.github/workflows/ci.yml` has exactly one job and never references either script).
- Is the lack of a shared `Protocol`/ABC for the Tier‑0 DEX aggregator clients (`DexScreenerClient`/`GeckoTerminalClient`/`DefiLlamaClient`) intentional, or should it mirror the EVM `EVMEnrichmentProvider` contract now that a third client exists?
- No static type-checker (`mypy`/`pyright`) is configured anywhere in the repo (`pyproject.toml` has no `[tool.mypy]`/`[tool.pyright]` section, and CI never runs one). All `Protocol`-based contracts (`EVMEnrichmentProvider`, `Strategy`) are therefore unchecked at build time — is that a deliberate scope decision, or a gap to close?
- The single-DuckDB-writer, single-process deployment topology is implicit (absence of IaC/containerization) rather than explicitly documented as a constraint anywhere. If multi-host or horizontally-scaled ingestion is ever planned, this repo has no migration story for it (see Deployment & Topology Constraints) — worth an explicit ADR either way.
- `pyproject.toml:9` declares `requires-python = ">=3.10"` while CI pins exactly `3.12` (`ci.yml:24`) — is 3.10/3.11 actually supported, or should the floor be raised to match what's tested?
